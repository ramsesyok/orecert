# orecert 実装調査・レビュー

> この文書は修正前の調査記録です。その後の修正内容・利用方法は[利用ガイド](README-ja.md)と[修正記録](security-fixes-2026-09.md)を参照してください。

調査日: 2026-09-22。対象: コミット `9232e62` のソースと、作業フォルダに残っていた `orecert.exe`。製品コード・既存テスト・設定は変更していない。

## 結論

証明書作成と形式変換の基本機能は実装済み。ただし、秘密鍵保護・設定読み込み・出力先の検証に重大な不具合があり、現在のままで安心して社内配布できる完成状態ではない。

仕組みは「自己署名のルートCAを作り、そのCAでサーバ／クライアント証明書を署名する」方式。各サーバ証明書を個別に自己署名する方式ではない。利用先にルートCAを信頼させる処理は実装されていない。

## 実装状況

| 機能 | 状況・確認結果 |
| --- | --- |
| `init-ca` | RSA-2048、ECDSA P-256、Ed25519のCA生成処理あり。鍵・証明書・初期CRLファイルを出力 |
| `issue` | server/client/both、鍵・CSR・証明書・fullchain・meta.jsonの生成あり |
| アルゴリズム | RSA・ECDSA・Ed25519のサーバ証明書発行をCLIで確認。ただしYAMLのRSA鍵長指定に不具合あり |
| SAN | DNS/IP/URI/EMAILの抽出処理あり。不正なIPやURI、一部の未知指定はエラーにならず脱落する |
| PEM | RSAはPKCS#1、ECDSAはSEC1、Ed25519は非暗号化PKCS#8。証明書とfullchainもPEM |
| PKCS#12 | `.p12` の生成あり。3アルゴリズムとも秘密鍵・証明書・CAチェーンの復号確認済み |
| JKS | `.jks` の生成あり。3アルゴリズムともJava 17.0.2のkeytoolでPrivateKeyEntryとして読み込み確認済み |
| `verify` | CAチェーン・有効期間の検証あり。client用途を誤って拒否する。ホスト名・失効状態の検証なし |
| `revoke` | CRLへのシリアル追加・CRL番号更新・署名処理あり。外部アプリへの配布や失効確認の強制は行わない |
| 秘密鍵暗号化 | 未実装。指定を無視して成功するため、単なる機能不足より危険 |
| パスワード取得 | `prompt:`、`file:` の解決は未実装。直接文字列だけが実際のパスワードになる |
| JSON・ログ・終了コード | JSON出力・ログレベル・仕様別終了コード・panic復旧は未実装。通常のエラー終了は1 |
| 複数形式フラグ | `-t all` は対応。`-t pkcs -t jks` の和集合は未実装（単一文字列フラグ） |
| インストール・配布 | READMEのリポジトリURLは`yourname`のまま。例示するprofiles/localhost.ymlも未同梱。CIはWindows amd64だけを生成 |
| OSへの登録・TrustStore | Windows/Linux/Javaへの信頼CA登録、専用TrustStore作成、DER出力は未実装。PFXという名前での出力オプションもなし |

P12とPFXは同じPKCS#12系の形式であり、拡張子を変えるだけで信頼登録が完了するものではない。利用先の対応アルゴリズム・読み込み条件・信頼設定は別途必要。

## 優先して修正すべき不具合

P1は利用再開前に優先して修正、P2は機能の正確性・信頼性に関わる問題。以下の再現は、現行ソースから別名でビルドしたバイナリを一時ディレクトリで実行した結果。

### 1. P1: 同梱設定が構文不正で、空パスワードのバンドルができる

根拠: `.orecert.yaml:4`、`cmd/root.go:72`、`internal/bundle/bundle.go:48`。

`pkcs12_password: prompt:` は末尾のコロンが引用されておらず、YAML解析は `yaml: line 4: mapping values are not allowed in this context` で失敗する。しかし `initConfig` は読み込みエラーを返さず、コマンドを続行する。

同梱設定をそのまま使って `init-ca → issue → bundle` を実行すると成功し、生成P12の秘密鍵を空文字のパスワードで復号できた。設定ファイルを誤記・指定ミスした場合にもエラーが隠れる。

対処: サンプルは`'prompt:'`のように引用し、設定の不存在・構文不正は生成処理前に必ず失敗させる。空パスワードも拒否する。

### 2. P1: パスワード取得方式をそのままパスワードとして使用する

根拠: `internal/bundle/bundle.go:17`、`:48`、`:56`。

構文だけ直して `pkcs12_password: 'prompt:'` としても対話入力は出ない。生成されたP12は既知の文字列`prompt:`で復号できた。`file:password.txt`も、ファイルの中身ではなく文字列`file:password.txt`で復号できた。

ファイルを取得した第三者に対して、意図したパスワード保護が成立しない。JKSにも同じ値が渡される。

対処: direct/prompt/fileを明示的に解析し、非エコー入力・ファイル読み込み・空値拒否を共通実装する。未対応の方式を成功扱いにしない。

### 3. P1: `encrypt_key: true`でも秘密鍵が平文で保存される

根拠: `internal/issue/issue.go:37`、`:146`、`:169`、`:274`。

Profileに`encrypt_key`と`key_pass`が存在せず、YAML読み込み時も未知のキーを拒否しない。暗号化指定を付けて発行した秘密鍵は`RSA PRIVATE KEY`で、パスワードなしに解析できた。meta.jsonも常に`key_encrypted: false`。

対処: 暗号化PKCS#8の保存と読み戻しを実装する。それまで暗号化指定を明示的な未対応エラーにする。

### 4. P1: `cn: ca`で既存CAの秘密鍵・証明書を破壊できる

根拠: `internal/issue/issue.go:56`、`:90`、`:146`、`:152`。

既定CAパスで`overwrite: true`を設定し、`cn: ca`のプロファイルを発行すると、CAを読み込んで署名した後に、同じ`certs/ca/key.pem`と`certs/ca/cert.pem`をサーバ用の鍵・証明書で上書きする。処理は成功扱い。既存CAの鍵を失い、以降の発行・検証・失効運用が壊れる。

対処: CAディレクトリ名を予約するだけでなく、設定されたCAパスと出力先の衝突を正規化後に比較して禁止する。Windowsの大文字小文字の扱いにも注意する。

### 5. P1: `bundle`だけCNのパス検証がなく、`certs`外を読み書きする

根拠: `internal/bundle/bundle.go:25`〜`:33`。

`cn: ../outside`を渡すと、`outside/key.pem`と`outside/cert.pem`を読み、そこに`bundle.p12`と`bundle.jks`を出力することを確認した。他コマンドのCN検証も呼ばれていない。

悪意ある／誤ったプロファイルを実行させる必要があり、対象には解析可能な鍵・証明書が必要。任意内容の任意ファイルへの書き込みではないが、想定外の秘密鍵のバンドル化や既存バンドルの破壊につながる。

対処: CN検証を共通化し、正規化した出力先が生成物ルート内にあることを確認する。CA領域への出力も禁止する。

### 6. P2: `rsa_bits`がYAMLから反映されない

根拠: `cmd/issue.go:35`、`internal/issue/issue.go:41`、`:81`。

Profileは`mapstructure:"rsa_bits"`しか持たない一方、実際の読み込みは`yaml.Unmarshal`。`rsa_bits: 4096`を指定してもRSABitsは0となり、2048bit鍵が生成された。

対処: 正しい`yaml`タグを付ける。2048/3072/4096の許容値検証と、CLIから生成した証明書の公開鍵長を確認するテストを追加する。

### 7. P2: 正しく発行したクライアント証明書の検証に失敗する

根拠: `internal/verify/verify.go:53`。

`issue -t client`で発行した直後の`verify`が`verify failed`になった。GoのVerifyOptionsでKeyUsagesを省略するとServerAuthが使われるため、ClientAuth専用証明書は拒否される。

対処: 検証対象の用途を選択できるようにして、用途に応じたEKUを検査する。単にすべての用途検証を無効化して回避しない。

仕様の根拠: [Go crypto/x509](https://pkg.go.dev/crypto/x509#VerifyOptions)。

### 8. P2: `bundle`が`overwrite: false`を無視する

根拠: `internal/bundle/bundle.go:17`、`:99`、`:116`。

ConfigにOverwriteがなく、P12はWriteFile、JKSはCreateで無条件に置き換える。上書き禁止設定で2回実行すると両方成功し、P12の内容が変わることを確認した。

対処: 出力する全形式の衝突を事前確認する。可能なら一時ファイルから確定し、途中失敗で片方だけ更新されないようにする。

### 9. P2: 秘密鍵と証明書が不一致でもバンドル作成が成功する

根拠: `internal/bundle/bundle.go:33`〜`:48`、`:108`。

2つの証明書を発行し、片方のkey.pemだけをもう片方のものに差し替えてからbundleを実行すると、P12/JKSの両方を成功扱いで生成した。配備先で鍵が使えず、障害原因が分かりにくくなる。

対処: 鍵の公開鍵と証明書の公開鍵の一致、指定CAとの署名関係を変換前に検証する。

### 10. P2: PKCS#12に古い暗号設定を固定使用している

根拠: `internal/bundle/bundle.go:94`、依存go-pkcs12 v0.5.0の`Encode`実装。

`pkcs12.Encode`はLegacyRC2エンコーダを呼び、証明書部にRC2-40、秘密鍵部に3DES、MACにSHA-1を使用する。秘密鍵がRC2-40で暗号化されるわけではない。依存ライブラリ自身がこのAPIを非推奨としており、Modernエンコーダも既に備える。

対処: 利用先の互換性を確認してModernを既定にする。旧形式が必要な場合は互換モードとして明示選択にする。今回のJavaでの読み込み成功は、安全な暗号設定の保証ではない。

## 安全性・仕様上の不足

- **失効確認をしない**: `issue → revoke → verify`で最後のverifyは成功した。Goの証明書VerifyもCRL検査をしない。現行要求仕様のverifyはチェーンと期限の検査だけなので、これはその仕様を含めた不足として扱う。CRL生成だけでは各サーバ／クライアントに失効は反映されない。[Goの説明](https://pkg.go.dev/crypto/x509#Certificate.Verify)
- **ホスト名を検証しない**: VerifyOptions.DNSName未指定。SANなしでもチェーン検証は成功するため、「TLSサーバとして接続可能」の保証にはならない。
- **入力検証が弱い**: 不正IP/URIの黙示的な除外、負のdays、CAを超える有効期間などを事前拒否していない。SANのメタ情報は元入力を記録するため、証明書に実際に入ったSANと食い違う場合がある。
- **ファイル保護が不足**: P12は0644、JKSはos.Createの0666（Unixではumask適用）で作成する。秘密鍵入りバンドルも0600相当に制限すべき。PEM秘密鍵は0600指定だが、WindowsでUnixのmode指定は専用ACL設定の代わりにならない。実際の他ユーザーからの可読性は親フォルダのACL次第で、今回は未検証。
- **途中失敗時の整合性**: 鍵から順に直接書き込むので、上書き中に証明書保存が失敗すると鍵と証明書の組が壊れ得る。保存途中の障害からの復旧機構はない。
- **CRL管理が限定的**: 初期CRLはヘッダだけで有効な署名付きCRLではない（現行仕様どおり）。既存CRLの署名・失効対象の発行元確認・重複排除はない。CA再作成時も古いCRLを残す。
- **生成物がGitの除外対象でない**: `.gitignore`にcerts/や秘密鍵の除外がなく、通常の作業で秘密鍵を誤コミットする余地がある。
- **設定仕様の不一致**: 環境変数禁止の仕様に対してAutomaticEnvが有効。設定の暗黙探索は実行ファイルのディレクトリだが、ヘルプはHOMEと記載。相対パスは設定ファイル基準ではなく実行時ディレクトリ基準。

## 既知脆弱性の検査

### 現行ソースを現在のGoでビルドする場合

環境はGo 1.26.4/windows/amd64、govulncheck v1.4.0。`govulncheck ./...`で到達可能な標準ライブラリの既知脆弱性を1件検出した。

- [GO-2026-5972 / CVE-2026-33818](https://pkg.go.dev/vuln/GO-2026-5972): encoding/asn1の再帰深度制限不足。検出経路はIssue → x509.CreateCertificateRequest → asn1.Unmarshal。Go 1.26系では1.26.6で修正。

到達可能なシンボルがあることは、orecertの入力から実際に攻撃可能であることと同義ではない。悪用入力を作った攻撃実証は行っていない。更新済みのサポート対象Goで再ビルド・再検査する必要がある。

加えて、importするパッケージには10件、requireするモジュールには24件を検出したが、今回のソース解析では該当する脆弱な関数の呼び出しは検出されなかった。これらを一律に「このツールで悪用可能」とは判断していない。

### 作業フォルダの既存orecert.exe

`go version -m orecert.exe`の結果はGo 1.24.3、元コミット`374dc59fc1a9407018589986e16495d77e38cf58`。現行HEADとは別のビルド。

`govulncheck -mode=binary orecert.exe`は標準ライブラリの脆弱なシンボルを15件検出した。バイナリ検査のため、各ケースの実際の入力到達性・悪用可能性までは判断していない。

検出ID: GO-2026-5972、5037、4971、4947、4946、4601、およびGO-2025-4175、4155、4013、4011、4010、4009、4007、3750、3749。

特に証明書・PEM・ASN.1の解析や検証を扱うツールなので、このexeをそのまま再配布せず、修正版Goと修正後のソースから作り直す。

## テスト・ビルド・CI

実施結果:

- 現行ソースの`go build -buildvcs=false`は成功。
- `go vet ./...`は成功。
- `go test ./... -count=1 -coverprofile=coverage-review.out`はWindows上で失敗。主因はテストがos.Chdirしたまま元のディレクトリに戻らず、t.TempDirの削除が「別のプロセスが使用中」で失敗すること。通常のTDDの前提となる安定したテスト実行を直す必要がある。
- 上記の不具合再現は、既存テストとは別の一時テストで、子プロセスのDirを切り替えて実施した。期待する安全な動作をassertし、対応する不具合で失敗することを確認した。修正は今回の対象外。

CI・READMEはGo 1.22を示す一方、go.modの最低バージョンは1.24.3。自動ツールチェーン取得の可否に依存するため統一が必要。CIにテスト実行・カバレッジ判定・脆弱性検査はない。

## 次に行う修正の順序

1. 設定の厳密な読み込み、パスワード解決、暗号化指定の扱いを直し、意図しない平文・空パスワードを防ぐ。
2. CAと出力パスの衝突、CNの検証、上書き禁止、保存途中の整合性を直す。
3. YAMLの鍵長・EKU検証・バンドルの鍵一致を直し、失効確認／ホスト名確認の範囲を仕様化する。
4. Windowsのテスト後処理を直す。不具合ごとに再現テストを先に追加し、修正→リファクタリングの順で進め、全体90%以上とテスト成功をCIで要求する。
5. Go・依存・CIを更新して再ビルドし、対象Windows、Linux、Javaの実アプリで相互運用を確認する。

今回の相互運用確認はWindows上でのCLI、GoによるP12復号、Java 17のJKS読み込みまで。Windows証明書ストア/IIS、Linux/OpenSSL/nginx、Javaアプリでの実際のTLS通信・失効適用までは未実施。
